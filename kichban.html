2Hợp đồng GET /api/dishes mới

Block6 trả mảng món. Block7 trả một trang kèm metadata, vẫn trong envelope ok / data / error. Mọi nơi đang dùng danh sách món (thực đơn, admin) đã đổi theo.

Request

GET /api/dishes?mode=advanced&q=gỏi&tag=12
    &minPrice=50000&maxPrice=150000&available=true
    &sort=gia-tang&page=2&pageSize=12
  • mode: basic (mặc định) · advanced · fulltext · fuzzy
  • page ≥ 1 (mặc định 1) · pageSize 1–100 (mặc định 12)
  • q: bắt buộc ở fulltext, fuzzy
  • sort: ten · gia-tang · gia-giam · moi-nhat (basic, advanced; moi-nhat = id giảm, giữ trong API, admin không dùng nữa)
  • tag, minPrice, maxPrice, available: chỉ advanced, nối bằng AND
  • searchIn=name,tag: admin tìm cả tên tag (basic)

Response 200

{ "ok": true, "data": {
    "items": [ { "id": 806, "name": "…", "price": …,
                 "chef": { "id": 14, "name": "…" },
                 "tags": [ { "id": 1, "name": "Khai vị" }, … ] }, … ],
    "total": 14, "page": 2, "pageSize": 12 } }
  • total đếm cùng điều kiện với items; còn trang sau khi page × pageSize < total.
  • fulltext, fuzzy: mỗi món có thêm score (3 chữ số), xếp theo điểm rồi id.

Các trường hợp biên

Tag: GET /api/tags → [{ id, name, dishCount, chefCount }]; POST /api/tags {"name"} (trùng không phân biệt hoa thường → VALIDATION_FAILED). Món và đầu bếp ghi bằng tagIds (≥ 1, id có thật). Bảng đầy đủ trong README.md.

3Luồng từng thao tác: URL trang ↔ request API ↔ SQL

Browser URL trên thanh địa chỉ (trang của SPA)   SPA đọc URL, gọi API, cập nhật danh sách   API validate, dựng điều kiện   DB câu SQL thật (bật LOG_SQL=1, bản đầy đủ trong evidence/sql-log/)

A. Số trang: bấm trang 2

  1. BrowserNút trang 2 là link → URL /dishes?page=2 (History API, không tải lại document).
  2. SPAreadQuery(URL) → toApiParams → GET /api/dishes?mode=basic&page=2&pageSize=12. Request của URL trước (nếu chưa về) bị huỷ bằng AbortController.
  3. APIparseListQuery: page = 2, pageSize = 12, không có tiêu chí → where = {}.
  4. DBTrong một transaction REPEATABLE READ: 
    SELECT COUNT(*) … FROM dishes WHERE 1=1                                → 1200
SELECT … FROM dishes WHERE 1=1 ORDER BY id ASC LIMIT $1 OFFSET $2      params: ["12","12"]
SELECT … FROM chefs WHERE id IN (…) · dish_tags · tags                  ← chỉ cho 12 món của trang
  5. SPA{ items: 12, total: 1200, page: 2, pageSize: 12 } → thay danh sách, "Món 13–24 trong 1200 món", cuộn mượt về đầu danh sách và đưa focus tới đó.

B. Tải thêm và Cuộn vô hạn: nối trang 3

  1. BrowserBấm "Tải thêm" (view=more) hoặc phần tử canh cuối danh sách vào vùng nhìn (view=scroll, IntersectionObserver, sớm 200px). URL không đổi.
  2. SPACả hai gọi loadNext(): đang tải hoặc đã hết → thoát; đặt cờ đang tải trước khi gửi → GET /api/dishes?mode=basic&page=3&pageSize=12.
    Bấm 3 lần liên tiếp: lần 2, 3 thấy cờ đang tải → chỉ 1 request page=3.
  3. DBNhư A với OFFSET 24.
  4. SPAResponse còn thuộc điều kiện hiện tại → nối 12 món (hiện dần), nextPage = 4, "Đã hiện 36/1200 món"; end khi page × pageSize ≥ total.
    Lỗi mạng: giữ 24 món, nextPage vẫn 3, nút thành "Thử lại" → tải đúng trang 3. Cuộn vô hạn ngắt observer khi lỗi để không gọi API liên tục.

C. Đổi điều kiện khi request cũ chưa về

  1. BrowserĐang ở Tải thêm, bấm "Tải thêm" (request trang 2 chậm) rồi bấm ngay chip "Đồ uống" → URL /dishes?mode=advanced&tag=11&view=more.
  2. SPAKhoá điều kiện đổi → huỷ request cũ, tăng "thế hệ", xoá danh sách, tải trang 1 của điều kiện mới. Ngay lần render đầu đã hiện khung xương, không hiện danh sách cũ.
  3. SPAResponse trang 2 cũ (nếu vẫn về) mang thế hệ cũ → bị bỏ. Danh sách chỉ có 12 món Đồ uống (total 86).

D. Tìm cơ bản "100%" (ký tự đặc biệt)

  1. BrowserGõ "100%" (URL chưa đổi, chưa gọi API), Enter → /dishes?q=100%25.
  2. SPAGET /api/dishes?mode=basic&q=100%25&pageSize=12
  3. APIescapeLike("100%") → 100\% → Prisma contains, mode: "insensitive".
  4. DBWHERE name ILIKE ('%' || $1 || '%')   params: ["100\\%", …] (log in dạng JSON) → chỉ "Combo 100% bò".

E. Nâng cao: "gỏi" + Hải sản + 50.000–150.000đ + còn phục vụ, giá tăng dần

  1. BrowserChọn "Nâng cao", nhập tên và giá → Tìm; ô Tag, Trạng thái, Sắp xếp áp dụng ngay khi đổi. Mỗi lần áp dụng: URL mới, bỏ page (về trang 1).
  2. DB 
    WHERE name ILIKE ('%' || $1 || '%')
  AND EXISTS (SELECT … FROM dish_tags t0 WHERE t0."tagId" = $2 AND t0."dishId" = dishes.id)
  AND price >= $3 AND price <= $4 AND available = $5
ORDER BY price ASC, id ASC LIMIT … OFFSET …        params: ["gỏi", 12, 50000, 150000, true, …]
    COUNT(*) cùng điều kiện → total: 14; trang 2 có 2 món.

F. Toàn văn "nước dùng xương"

  1. SPAGET /api/dishes?mode=fulltext&q=nước+dùng+xương&pageSize=12; ô sắp xếp khoá ("Theo độ phù hợp").
  2. DBMột câu SQL trả cả total và id + điểm của trang: 
    WITH input AS (SELECT plainto_tsquery('simple', $1) AS query),
docs AS (SELECT id, setweight(to_tsvector('simple', coalesce(name,'')), 'A')
                 || setweight(to_tsvector('simple', coalesce(description,'')), 'D') AS document FROM dishes),
matched AS (SELECT id, round(ts_rank(document, query)::numeric, 3) AS score
            FROM docs, input WHERE document @@ query)
SELECT count(*) …, json_agg(… ORDER BY score DESC, id ASC LIMIT $2 OFFSET $3)
  3. APINạp tag, đầu bếp của các id bằng Prisma, giữ đúng thứ tự điểm → 62 món, đầu tiên "Hủ tiếu xương khô" (có "xương" trong tên, trọng số A).

G. Gần đúng "bò lúc lắt" (gõ sai)

  1. DBTrong cùng một transaction: 
    SELECT set_config('pg_trgm.similarity_threshold', $1, true)     params: ["0.3"]   ← SET LOCAL
WITH matched AS (SELECT id, round(similarity(name, $1)::numeric, 3) AS score
                 FROM dishes WHERE name % $2)                    params: ["bò lúc lắt", …]
SELECT count(*) …, json_agg(… ORDER BY score DESC, id ASC LIMIT $3 OFFSET $4)
COMMIT
  2. SPA6 món: Bò lúc lắc 0.667, Cơm bò lúc lắc 0.5, Cơm tấm bò lúc lắc 0.4, Cơm niêu bò lúc lắc 0.381, Cơm bò lúc lắc phần lớn 0.333, Lẩu bò 0.308.
    "pho bo tai" (không dấu) → 0 món, kèm gợi ý gõ có dấu: giống "Phở bò tái" ≈ 0.22 < 0.3.

H. Reload, mở lại link, URL sửa tay

  1. BrowserReload /dishes?q=phở&page=2 → Vite trả index.html, SPA đọc URL → đúng trang 2 của "phở" (ô tìm có sẵn "phở").
  2. BrowserReload /dishes?q=phở&view=more → tải lại từ đầu (12 món), giữ điều kiện — chính sách đã công bố cho Tải thêm / Cuộn.
  3. BrowserSửa tay ?page=0 hoặc ?mode=advanced&minPrice=abc → VALIDATION_FAILED → lỗi cạnh ô + "Điều kiện tìm không hợp lệ" + "Xoá bộ lọc"; không trang trắng.
    ?page=101 → "Trang 101 không có món nào." + link "Về trang cuối (100)".

5Lỗi đã phát hiện và cách sửa

Lỗi chính: ký tự người dùng gõ bị hiểu là wildcard (bước 7)

Tái hiệnBản đầu: where: { name: { contains: q, mode: "insensitive" } }. GET /api/dishes?q=%25 và ?q=_ → total 1200; ?q=Trà_ → nhiều món "Trà …" (vd. "Trà matcha sữa") thay vì chỉ "Trà_sữa nhà làm".
Nguyên nhânPrisma sinh "name" ILIKE ('%' || $1 || '%') và đưa $1 nguyên vẹn: % = chuỗi bất kỳ, _ = một ký tự bất kỳ. Tham số bind chống SQL injection, không giữ nghĩa "chứa đúng chuỗi". Agent viết theo mặc định của Prisma, không kiểm chứng.
Cách sửaescapeLike (api/src/validators/list-query.js): \ → \\, % → \%, _ → \_ trong một lượt thay thế, trước khi đưa vào contains. Dấu \ là ký tự escape mặc định của LIKE/ILIKE. Áp dụng cho cả tìm tên và tìm tag (admin).
Bằng chứng sau khi sửa?q=%25 → 1 món (560), ?q=_ và ?q=Trà_ → 1 món (700), ?q=%5C → 1 món (960); log SQL: params: ["100\\%", …]; wildcard-escape.sql chạy cả hai phiên bản trên database (1200 / 1200 / 23 → 1 / 1 / 1 / 1); check-api.sh phần D kiểm tra lại mỗi lần chạy.
